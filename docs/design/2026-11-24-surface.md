# `Surface`: a box the program's code draws, and takes fingers on

Status: design agreed in discussion 2026-11-24 · steps 1 to 4 of "Order
of building" are built: several fingers, the pointer sample, `on:hover=`,
`on:wheel=`; `Surface` with `draw=picture`, `draw=commands` and
`draw=gpu`; `depth=true`. NOT built: `capture_mouse=` · the examples here are not
compiled, and the Rust names of what is not built are sketches. What is
built is in `docs/REFERENCE.md` "Surface", with compiled examples.

The user ruled every point of this design (2026-11-24, four rounds); the
rulings are marked **RULED**. No point is open. The Rust names stay
sketches until the code is written.

## Why

A page often has a part that no `.gogo` word can describe: the painting
of a paint program, the world of a game, a 3D preview of an item. The
program's code draws that part, and the fingers on it belong to the code:
one finger paints, two fingers zoom.

Today gogo and TurboDot have four ways to do this, and the page's file
shows none of them:

- **A code picture.** `Image source="preview://brush"`. The file says
  `Image` with what looks like a file address. In truth the code hands
  the renderer a texture under that name
  (`UiRenderer::set_external_image`).
- **A host layer.** The same `Image` spelling. When the code opened the
  name with `UiRenderer::host_layer`, the Image draws no picture: the
  code's own GPU draw calls run at that point of the pass. They get the
  whole screen, not the Image's own rectangle, and the pass has no depth
  buffer.
- **A code control.** A node type the program lists in
  `CompileOptions::code_controls`. In the file it is an empty box
  (warning G7013). The code reads the box's rectangle and draws there.
- **`Page::gpu_draw_screen`** (TurboDot). Draw commands that go under all
  of a page's nodes. The file does not mention them.

Fingers are a fifth thing: `interactive=true` with `on:pointer=`. A
pointer event carries no finger id and no pressure, and gogo follows one
press per page. A second finger does nothing, so a page cannot tell a
pinch from a drag, and a game cannot hold a joystick and press a button.

Someone who opens such a page six months later reads
`Image source="stickers://layer"` and expects a picture. Nothing tells
them that code draws there, how it draws, or who gets a finger that lands
on it.

`Surface` is one node kind for all of it. The file says where the code
draws, how it draws, and whether it takes fingers.

## The node

```kdl
View main {
    Layers width=fill, height=fill {
        Surface painting draw=commands, width=fill, height=fill,
            interactive=true, on:pointer=painting_pointer
        Panel toolbar valign=bottom, height=56 { }
    }
}
```

- **RULED: its own keyword**, `Surface`.
- A `Surface` has no children. What goes over it or under it is a node
  beside it in a `Layers`, as in the example: the toolbar is above the
  painting because it comes later.
- A `Surface` has no size of its own. It takes the size its words give
  it, or `fill`. In a parent that asks its children for their size it
  answers 0.
- It takes the words every node takes: size, alignment, margins,
  `visibility=`, `opacity=`, and the transform words, with the limits
  under "`draw=gpu`" below.

### `draw=`: how the code fills it

**RULED: the file must say it.** A `Surface` without `draw=` does not
compile. There is no default, so nobody gets one kind of drawing by
forgetting to ask for another.

| `draw=` | The code hands over | Cost while nothing changes | gogo does for free |
|---|---|---|---|
| `picture` | one texture, once | none | `fit=`, `sampling=`, `window=`, turn, slide, fade, clip |
| `commands` | gogo draw commands: rectangles, pictures, text | none: gogo keeps the list | turn, slide, fade, clip |
| `gpu` | its own GPU draw calls, inside the pass | the calls themselves | slide and clip |

**RULED: the three values** are `picture`, `commands` and `gpu`.

**RULED: the code pictures move here.** `Image source=` goes back to one
meaning, a picture file. An `Image` whose source is not a file is a
compile error that names `Surface draw=picture`.

**`draw=picture`.** The code hands gogo a texture when the texture is
another one than before. gogo draws it as it draws an `Image`: the words
`fit=`, `sampling=` and `window=` are legal on such a `Surface` and mean
what they mean on an `Image`. A frame in which the texture did not change
costs the code nothing.

**`draw=commands`.** The code writes a list of gogo draw commands in the
`Surface`'s own space: (0, 0) is its top left corner, in epx. gogo keeps
the list and draws it every frame, moved to where the `Surface` is. gogo
asks the code for a new list in three cases: the `Surface` shows for the
first time, its size changed, or the code said its content changed. A
change of the list does not make gogo build the page's own draw list
again, and a change of the page does not make gogo ask for the list
again.

**`draw=gpu`.** For 3D, for a shader of the code's own. The code's draw
calls run inside the pass that draws the pages, at the `Surface`'s place
among the nodes: over what comes before it, under what comes after it.
There is no pass of its own and no copy.

- gogo sets the viewport to the `Surface`'s own rectangle and the scissor
  to the part of it that shows. The code draws as if the `Surface` were
  its whole screen. A page that slides in carries the `Surface` with it,
  and the code does nothing for that.
- gogo hands the code the rectangle in device pixels, the part that
  shows, the pixels per epx, the opacity (the code applies it if it
  wants), the target's format and the depth format.
- After the calls gogo sets its own state again. The code leaves the pass
  in any state it likes.
- **RULED: no transform.** A viewport is an upright rectangle, so gogo
  cannot turn or scale what the code draws. A turn written in the file on
  a `draw=gpu` Surface, or on a node above it, is a compile error. A turn
  the code writes at run time stops a debug build with a message that
  names the `Surface`. A phone that the user turns needs none of this:
  the window gets a new size and the `Surface` a new rectangle.

### `depth=true`

```kdl
Surface world draw=gpu, depth=true, width=fill, height=fill
```

- Legal only with `draw=gpu`.
- **RULED: per build.** The compiler knows every page of the program. If
  no `Surface` says `depth=true`, the program never makes a depth buffer
  and its pipelines are built without one: a 2D program pays nothing. If
  one does, every frame of the program has a depth buffer. gogo clears it
  when the frame starts and throws it away when the frame ends, so on a
  phone it costs memory (about 10 MB at 1080 x 2400) and nearly no time.
- gogo's own drawing never reads or writes depth.
- Two `Surface`s with depth in one frame do not see each other's depth:
  gogo clears the depth inside a `Surface`'s rectangle before that
  `Surface` draws, when it is not the first one of the frame.
- Not in this version: a stencil, and smoothing of edges for the whole
  pass (MSAA). A world that needs them draws into a texture of its own
  and shows it with `draw=picture`. That costs one pass more. It is also
  the way to draw a world at a lower resolution than the UI.

## Fingers

**RULED: several fingers at once, on every node.**

1. Each finger has its own press. A finger on a slider and a finger on a
   button work at the same time.
2. A node other than a `Surface` holds one finger at a time. While a
   finger holds a button, a second finger on the same button does
   nothing, from its landing to its lift: it does not go on to the node
   under the button either. A `Scroll` or a `List` that a finger pans
   counts as held by that finger.
3. A `Surface` takes every finger that lands on it. Each finger stays
   with the `Surface` until it lifts, wherever it moves.
4. Keyboard focus and the text caret stay single.

**RULED: a `Surface` takes fingers when it says `interactive=true` and
`on:pointer=<name>`**, as every node does today. `on:pointer=` without
`interactive=true` does not compile (G0073, an error today; **RULED**:
it stays an error). A `Surface` with neither lets a finger through to what is under
it.

### What a pointer event carries

Every `on:pointer` event, on any node, gains three fields:

| Field | Meaning |
|---|---|
| `finger` | the id the platform gave the finger; the same from its landing to its lift. A mouse has one fixed id. |
| `pressure` | the platform's number, unchanged. 1 when the device measures none. |
| `time` | when the platform took the sample, in seconds. Not when the event reached the page. |

**RULED: pressure is what the device says.** gogo does not change the
number and does not guess. A phone screen that measures no pressure
reports 1 for a finger, and a mouse reports 1. A pen, and a screen that
does measure, report a number between 0 and 1. What a brush does with a
1 is the program's rule, not gogo's.

**RULED: high rate, no allocation.** A phone takes several samples of a
finger between two frames, and a brush needs every one of them. The host
hands the program each sample, in the order the platform took them. Each
becomes one pointer event for the page. The buffer for the events is
kept from frame to frame: a sample allocates nothing. A count in the
perf suite holds that at 0.

### A mouse (RULED)

A program on a PC needs three things a finger does not have: the mouse
over the painting with no button down (a brush outline follows it), its
other buttons (the middle one pans), and its wheel (zoom at the mouse).

**A mouse is one pointer with a set of buttons.** It is not one pointer
per button.

- Every pointer event gains a fourth field, `buttons`: the buttons that
  are down at that sample, out of `primary`, `middle` and `secondary`. A
  finger is always `primary`.
- A mouse's stream starts (`Down`) when its first button goes down on
  the node, and ends (`Up`) when its last button lifts. A second button
  that goes down or lifts in between arrives as a `Move` with another
  `buttons`. So "pan while the middle button is down" is one test in the
  code: a `Move` whose `buttons` has `middle`.
- A node other than a `Surface` reacts to `primary` only, as today.

Two new events, for what is not a press. Each needs `interactive=true`
and goes where `on:pointer=` may go, a box that is not a control:

| Word | Fires | Carries |
|---|---|---|
| `on:hover=<name>` | the mouse moved over the box with no button down; once more when it left | the position inside the box, or "left" |
| `on:wheel=<name>` | the wheel turned while the mouse is over the box | the position inside the box, and the notches: above 0 is away from the user |

- A box that does not write the word gets no such event, and pays
  nothing for a mouse that moves.
- `on:pointer=` keeps its meaning: a press, from landing to lift. It
  does not start to send moves with no button down, so the code of a
  box that has it today reads the same events as before.
- The wheel goes to the topmost node under the mouse that takes it: a
  `Slider` or a `Toggle` as today, or a box with `on:wheel=`. When none
  takes it, the `Scroll` or `List` around the mouse moves, as today.
- **RULED: `mods` now.** `pointer`, `hover` and `wheel` events carry the
  keys held at that moment (Shift, Ctrl, Alt), as a key event has them:
  Ctrl with the wheel, Shift with a drag.

Not in this version: the shape of the cursor, a trackpad's pinch and its
sideways scroll. A pen and a captured mouse follow.

### A pen (RULED)

A pen differs from a finger in four ways a program may use. It is a pen:
a paint program lets the palm rest on the screen while the pen draws. It
leans. It has a button on its side. And many screens see a pen before it
touches them.

- **`tool`**: what touches. `finger`, `mouse`, `pen`, or `eraser` (the
  other end of a pen). The platform says which; gogo does not guess it
  from the pressure.
- **`tilt`**: how far the pen leans from upright, in degrees. 0 is
  upright, 90 is flat on the screen.
- **`tilt_toward`**: the direction the pen's upper end leans to, in
  degrees on gogo's compass: 0 is up on the screen, clockwise, as
  `rotate=` counts.
- Both are 0 for a finger, for a mouse, and for a pen whose device
  measures no tilt.
- **The side button** is in `buttons`: a pen's first side button is
  `secondary`, its second is `middle`. They are a mouse's right and
  middle button: "the other action" has one name on both.
- **A pen above the screen** fires `on:hover=`, as a mouse with no button
  down does. The sample says `tool` is `pen` and carries its tilt and
  its buttons. A brush outline follows the pen before it touches.

Not in this version: the turn of a pen about its own axis, and how high
it is above the screen.

### A captured mouse (RULED)

A program may need a mouse with no place: no cursor, and moves that do
not stop at the edge of the screen. A game turns its camera that way, a
3D editor turns a model, a number is dragged past the screen's edge.

```kdl
Surface world draw=gpu, depth=true, width=fill, height=fill,
    interactive=true, on:pointer=world_input, on:hover=world_input,
    capture_mouse=true
```

- **RULED: the word is `capture_mouse=true`**, the usual name for it. It
  goes on a `Surface` and is a bool like any other: the file writes it,
  a `when` block writes it, or the code writes it at run time (true when
  play starts, false at a pause).
- **It is in effect only while three things are true:** the word is
  true, the `Surface`'s page is the top page, and the window has the
  keyboard. When a page opens over it (a pause menu), the mouse is free
  again with no code, and captured again when that page leaves. A user
  is never left without a cursor in front of a menu.
- **While it is in effect** the cursor is hidden, and everything the
  mouse does goes to that `Surface` with no search for the node under
  it: presses through `on:pointer=`, moves with no button down through
  `on:hover=`, the wheel through `on:wheel=`. `x` and `y` stay where the
  mouse was when it was captured.
- **`dx`, `dy`**: two new fields of every sample, how far the pointer
  moved since its last sample. For a free pointer they are in epx, so a
  pan with the middle button reads them as they are. For a captured
  mouse they are the mouse's own counts, before the system speeds them
  up; the program multiplies them by its own sensitivity.
- **RULED: every move arrives.** gogo hands the page each move the mouse
  reported, with its own time, and sums nothing. gogo does not assume
  what the moves are for: the code uses each one, or adds them up, or
  drops them. A move allocates nothing, as a finger's sample does not.
- On a device with no mouse the word does nothing.
- One `Surface` at a time. Two in one page that both say true: the
  first in the file has the mouse, and a debug build says so.
- **For a host with its own window:** the program says whether it wants
  the mouse captured (a function to read each frame), and the host does
  it. TurboDot's own window does it by itself.

A note on the word. gogo's older texts say "captured" for a press that
stays with its node until the finger lifts. This text says "stays with"
for that, and keeps "capture" for the mouse.

### The whole sample

`on:pointer=` and `on:hover=` hand the page one value with these fields
(`PointerSample`, a sketch):

| Field | Meaning |
|---|---|
| the phase, beside the sample | `Down`, `Move`, `Up`, `Cancel` from `on:pointer=`; `Over`, `Left` from `on:hover=`. Two types: a handler of `on:pointer=` matches the four phases of a press and no other. As built: the first sketch had one type with six values, and every handler of a press then owed an arm for two phases it never gets. |
| `x`, `y` | the place inside the box, in epx |
| `dx`, `dy` | the move since the last sample |
| `finger` | the platform's id |
| `tool` | `finger`, `mouse`, `pen`, `eraser` |
| `buttons` | which of `primary`, `secondary`, `middle` are down |
| `pressure` | the device's number; 1 when it measures none |
| `tilt`, `tilt_toward` | a pen's lean, in degrees |
| `time` | when the platform took the sample, in seconds |
| `mods` | the keys held |

### A page over a `Surface`

**RULED: one page declares a shared `Surface`.** When several pages work
on the same painting or the same world, the bottom page declares the
`Surface` and holds its fingers. A page above it is see-through where it
has no node, and lets a finger there go on to the page under it
(`Page::TAKES_EVERY_TOUCH = false`, as today). The world is then drawn
once in a frame, also while a page slides.

A page that wants the fingers first (one that moves a text over the
painting) declares a see-through `Surface` of its own over that place.

## The Rust side (TurboDot), as a sketch

```rust
impl Page<App> for MainPage {
    /// Before the pass: writes buffers, draws into textures of its own,
    /// hands a `draw=picture` Surface its texture.
    fn gpu_prepare(&mut self, host: &mut Host<App>, gpu: &Gpu) { }

    /// The list of a `draw=commands` Surface, when gogo asks for it.
    fn draw_surface(&self, app: &App, surface: CommandSurface, out: &mut SurfaceCommands) { }

    /// The draw calls of a `draw=gpu` Surface, inside the pass. Reads
    /// only: what it needs was written in `gpu_prepare`.
    fn draw_surface_gpu(&self, app: &App, surface: GpuSurface, pass: &mut wgpu::RenderPass<'_>, place: &SurfacePlace) { }

    fn handle(&mut self, host: &mut Host<App>, event: PageEvent<Handler>) { }
}
```

- **RULED: a name's type says how the Surface is filled.** The build
  writes the name of a `Surface` with a type of its own: `NAMES.painting`
  is a `CommandSurface`, `NAMES.world` a `GpuSurface`, `NAMES.preview` a
  `PictureSurface`. A function for one kind does not take another. When
  the file says `draw=commands` and the code wants GPU calls, the code
  does not compile. This is the second half of "not missed by accident".
- Fingers come through `handle`, like every other event.
- `gpu_prepare` is today's `gpu_draw_textures` under a name that says
  when it runs.
- With no GPU (a test that runs `Program` alone) a `Surface` draws
  nothing, and its fingers work. A page's logic is tested with no
  window. `Gpu::draw_program` draws every `Surface` into the picture it
  returns.

## What goes away

One way for each task. The rows not marked follow from the rulings and
were not ruled one by one.

| Today | Becomes |
|---|---|
| `Image` with a source that is not a file (**RULED**) | `Surface draw=picture` |
| `UiRenderer::host_layer`, `set_host_layer` | `Surface draw=gpu` |
| `Page::gpu_draw_screen`, `Layers` | `Surface draw=commands`, at the bottom of the page's `Layers` |
| a code control (`CompileOptions::code_controls`, G7013) (**RULED**) | `Surface` |
| `Page::gpu_draw_textures` | `Page::gpu_prepare` (the name only) |

## What it costs

- No pass of its own, for any of the three kinds.
- No allocation per frame and none per sample.
- `draw=picture` and `draw=commands`: no work in a frame in which they
  did not change.
- `draw=gpu`: per `Surface` and frame, gogo sets a viewport and a
  scissor, and binds its own pipeline again afterwards. A `Surface`
  between two UI nodes splits gogo's batch there, as a host layer does
  today.
- `depth=true`: see above.

## What breaks for a program that builds these crates

- A pointer event has three more fields.
- An `Image` with a code picture no longer compiles; its name in the
  code changes type.
- `UiRenderer::host_layer` and `set_host_layer` are gone. The renderer's
  `new` takes the depth format, and its `render` takes what draws the
  `draw=gpu` Surfaces.
- `Program::touch_finger` takes a sample with pressure.
- `Page::gpu_draw_screen` is gone, `gpu_draw_textures` has a new name.

## Order of building

Each step with its tests, each new test seen failing first, and the perf
counts before and after.

1. Several fingers, the whole pointer sample, `on:hover=` and
   `on:wheel=`. The largest step: gogo's press, with its scroll, fling,
   slider, toggle and text selection, is one today.
2. `Surface` with `draw=picture` and `draw=commands`. The code pictures
   move. `Page::gpu_draw_screen` goes.
3. `draw=gpu` with the viewport. The host layer goes.
4. `depth=true`.
5. `capture_mouse=`.

## The rulings, by round (2026-11-24)

No point is open.

1. The keyword `Surface`; the code pictures move under it; several
   fingers on every node in one step, with every sample and no
   allocation; one page declares a shared `Surface`; a depth buffer,
   declared and per build; the code's own GPU drawing declared, and the
   declaration required; the four finger rules.
2. The three values of `draw=`; every `Surface` writes `draw=` and the
   name's type holds the code to it; the code control retires into
   `Surface`; `interactive=true` stays needed; pressure is the device's
   number; a second finger on a held node does nothing; no transform
   for `draw=gpu`.
3. G0073 stays an error; the mouse is one pointer with `buttons`;
   `on:hover=` and `on:wheel=`; `mods` now.
4. The pen: `tool`, `tilt`, `tilt_toward`, the side buttons, hover above
   the screen. The captured mouse: the word `capture_mouse=`, every move
   arrives, `dx` and `dy` with their two units.

## As built, step 2 (2026-11-24)

What differs from the text above, or was left open by it:

- **The code control and the code picture are gone** as the table says.
  `Page::gpu_draw_screen` and `Layers` are gone, `gpu_draw_textures` is
  `gpu_prepare`, and `Page::DRAWS_GPU_PICTURE` is gone too: a
  full-screen page whose own code draws all of it has a Surface over the
  whole window, and the debug check of a page's kind reads that.
- **`draw_surface` gets no `host`**, as the sketch says: the commands
  being written hold the page. Its signature is
  `fn draw_surface(&self, app: &A, surface: CommandSurface, out: &mut SurfaceCommands)`.
- **A page hands a `draw=picture` Surface its texture** with
  `host.ui.set_picture_texture(surface, texture)` in `gpu_prepare`, or
  pixels with `host.ui.set_picture(surface, width, height, rgba)` from
  anywhere.
- **Not built: a picture among a TurboDot page's draw commands.** A
  `Draw::Image` names a picture by a key, and a page has no call that
  gives its own texture a key (`Layers::image` did). A host that keeps
  its own picture table has the key.
- **`clip_contents=true` on a `draw=commands` Surface** cuts its commands
  at its edge. Without it they may reach past the edge: a cut is an
  upright rectangle, which would be wrong for a Surface that is turned.
- **A `scale=` on a `draw=commands` Surface** moves its corner and does
  not shrink what the code drew. The table promises turn, slide, fade
  and clip, and those hold.

## As built, step 3 (2026-11-24)

- **The renderer keeps `render` and gains `render_with`.** The text had
  `render` take what draws the `draw=gpu` Surfaces. A host with no such
  Surface would then hand over a closure that is never called, so
  `render(pass)` stays for it, and stops a debug build when the frame
  does have such a Surface. `render_with(pass, draw_gpu)` calls the host
  once for each, in paint order.
- **A page's pipeline needs the pass's format before the pass.** The
  text hands the format over with the place, at the draw call, where
  the page can only read. A page asks `host.ui.target_format()` in
  `gpu_prepare` and makes its pipeline there.
- **A scale is no error.** The viewport is the Surface's rectangle as
  drawn, so a `scale=` on the Surface scales what the code draws. Only a
  turn has no way: `rotate=` written on the Surface or above it is G7017,
  and a turn or a swing in force when the frame is drawn stops a debug
  build with the Surface's name.
- **The place** a host is handed is `SurfacePlace`: the rectangle and
  the part that shows in device pixels, the pixels per epx, the opacity,
  the target's format, and `is_of(&page)`, since a node's id says
  nothing of its page. The depth format comes with step 4.
- **A Surface wider or taller than the device's largest viewport is not
  drawn**: the device would refuse the viewport.

## As built, step 4 (2026-11-24)

- **The format is 32-bit float** (`turbodot::DEPTH_FORMAT`), one format
  for every GPU. A host with its own frame loop picks its own and hands
  it to `UiRenderer::new`.
- **The depth is cleared to 1.0**, the far end. A world that wants its
  depth the other way round (0 far, which keeps more precision far
  away) cannot have it in this pass: the clear value is the pass's.
- **Every pipeline in the pass names the depth format**, also the
  pipeline of a `draw=gpu` Surface without `depth=true`: the GPU takes
  no other. The place says the format (`SurfacePlace::depth_format`) and
  whether this Surface said `depth=true` (`has_depth`).
- **The clear before a later Surface** is one triangle that writes depth
  1.0 and no color, over the part of the Surface that shows. gogo draws
  it before a `depth=true` Surface when ANY code drew earlier in the
  frame, also code of a Surface without `depth=true`: such code may have
  written depth. The text said "when it is not the first one".
- **`depth=` in a `when` is G7018**, and so is a `depth=` that is not
  written out as `true` or `false`. A hot reload refuses a saved file
  that changes a Surface's `depth=`: the pass was made at start.
- **The draw list carries no word of depth.** A renderer asks the page
  whether the Surface says `depth=true` (`Page::is_depth_surface`). A
  flag in the draw command was built first, and with it the walk that
  writes every page's draw list grew: GitHub counted 0.1 to 0.4 % more
  instructions for a frame after a change and for a list's open.
- **A debug build stops** when a `depth=true` Surface is drawn by a
  renderer made with no depth format. A release build tells the code
  that it has no depth (`has_depth` false).
- **`examples/world`** is a program with one: a cube under a label and a
  button. The notes example stays a program with no depth buffer.

## To check before building

- CHECKED with step 3: in wgpu 30 a viewport may reach past the edge of
  the target (its corner may lie up to twice the largest texture side
  outside, its size up to that side). The scissor may not, so gogo cuts
  it at the target's edge.
- CHECKED with step 4, by reading wgpu 30: its OpenGL ES backend takes
  every depth format as a render target, 32-bit float as
  `DEPTH_COMPONENT32F` (OpenGL ES 3.0), and so do Vulkan, Metal and
  Direct3D 12. NOT run on a phone: no program on a phone has a
  `depth=true` Surface yet.
- CHECKED with step 2: a code picture did take its size from its pixels
  in one place, TurboDot's `PageUi::set_picture` on an `Image size=hug`.
  A `Surface` has no size of its own, so that place writes one now.
- CHECKED with step 2: a full-screen page is known by a `Surface` that
  covers the whole window; `Page::DRAWS_GPU_PICTURE` is gone.
